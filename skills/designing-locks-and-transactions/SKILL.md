# 锁与事务设计

从业务约束推导互斥、原子提交和读取一致性的要求，再选择足够且简单的机制。明确区分正确性要求、工程约定和具体实现。

## 公理

以下是本技能接受的正确性要求；具体业务规则及可接受的数据视图，由当前任务确定。

| 公理 | 含义 |
| --- | --- |
| 并发不破坏业务约束 | 操作交错执行后，业务要求仍须成立，例如余额不能透支。 |
| 原子操作不部分生效 | 业务要求作为整体完成的修改，必须全部提交或全部撤销。 |
| 读取满足承诺的一致性 | 查询结果须符合用途要求；需要一致视图时，不能拼接互不一致的数据。 |

## 前提与工程约定

数据库原子提交的推论，以相关操作能纳入同一事务为前提。先沿实际调用链确认共享资源、冲突入口、锁机制、数据库隔离级别及事务传播。以真实的读取、提交和释放时机为依据，不仅看注解或方法边界；未确认的条件标为假设。

**默认约定：需要业务互斥时，优先复用适用的分布式锁，默认不主动增加 `FOR UPDATE` 等锁定读取。** 目的是减少不必要的数据库锁竞争与长事务，不代表分布式锁天然更安全或性能必然更好。普通数据库写入自身获取的锁仍属正常机制。

这项默认选择成立的前提是：所有相关冲突入口遵守同一锁规则，锁在保护期间持续有效，决策数据的读取符合所需时序。不能仅凭一次成功加锁就认定这些前提成立。

## 推论

| 判断依据 | 推导出的原则 |
| --- | --- |
| 纯查询不修改共享状态 | 默认不加业务互斥锁；多次查询需要一致视图时，按需使用合适隔离级别的快照事务。 |
| 并发可能使先前判断失效 | 保护完整的“读—校验—计算—写”；读取决策所需的可变数据前进入保护范围，不直接复用锁外旧值或旧事务快照。 |
| 数据库单条原子操作已满足业务约束 | 不额外增加分布式锁；存在写操作本身不是加锁理由。 |
| 多步修改不能分别生效 | 将这些修改纳入同一个数据库事务，确保失败时按预期回滚；锁不能替代原子提交。 |
| 没有跨步骤原子提交或一致快照需求 | 不强制包多语句事务；若选择行锁保护后续操作，事务仍必须覆盖这段操作。 |
| 互斥必须覆盖受保护修改的完成 | 分布式锁持续有效到实际提交或回滚完成；没有显式事务时，覆盖受保护操作的实际完成。 |
| 默认机制不足以保护业务规则 | 可以采用显式数据库锁，但说明不足之处、锁定记录或范围、索引及事务时长；不因“多实例”就认定行锁无效，也不默认叠加两种锁。 |

事务也提供隔离能力，但 `@Transactional` 本身不能证明业务已经串行。数据库锁在事务内提供并发保护；分布式锁在应用层协调业务过程。

分布式锁与事务共同使用时，默认顺序为：

```text
获取分布式锁
  → 开始事务
  → 读取、校验、计算、写入
  → 实际提交或回滚完成
释放分布式锁
```

确认内部方法没有意外加入拿锁前已经建立旧快照的外层事务。获取 Redis 锁不会刷新数据库快照。

采用显式数据库锁时：

```text
开始事务
  → 锁定读取相关记录
  → 校验、计算、写入
提交或回滚，释放数据库锁
```

范围以业务需要为界：避免无关资源互相阻塞，多把锁统一获取顺序，耗时外部调用尽量放在数据库事务外。

## 示例推演

假设余额为 100，两笔扣款各为 80，业务禁止透支。若两者都先普通查询、通过校验，再无条件扣减，就可能共同超支。因此，必须保护决定扣款的完整读写过程，默认采用满足上述前提的分布式锁。

若扣款还必须同步记录流水，串行执行仍可能出现“余额已扣、流水失败”，因此两步需要同一事务。若只是查询余额，则没有这段写入冲突，不需要业务互斥锁。

## 检验

对方案检查以下反例，只针对实际存在的问题调整：

- 两个请求同时读到旧值，是否仍可能共同通过校验并写入？
- 中间一步失败，是否留下业务不接受的部分提交？
- 获取分布式锁后，是否仍使用锁外数据或旧事务快照？
- 锁租约失效、存在绕过锁的写入口，或事务尚未结束时，是否仍被误认为处于互斥保护中？
- 显式数据库锁是否有明确必要性，其扫描范围或持有时间是否超出需要？

说明结论时，交代保护的业务规则、锁的对象和范围、事务边界，以及必要的例外依据；不必重复完整推演。
